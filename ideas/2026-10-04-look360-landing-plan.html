VR 촬영 의뢰와 콘텐츠 방문을 늘리려고 주제별 랜딩페이지를 여러 장 깔아 두는 계획이야. l3 플랫폼이 아니라 지금 운영 중인 레거시 look360.kr(PHP, AWS EC2)에 붙이는 것을 전제로 썼어.

한 줄 결론 총 24장을 4번(B1~B4)에 나눠 만들자. 첫 배치 6장은 시안이 모두 나와 있어 → 대학교 · 초·중·고 · 공공시설 · 관광지 · 비용 · 절차. 한 배치를 올리면 색인되고 반응을 볼 때까지 3~4주 기다렸다가 다음 배치로 넘어가.

1. 왜 24장인가

"낚시대를 많이 깔수록 좋다"는 맞는 말인데, 검색엔진에는 상한선이 있어. 지역명이나 업종명만 바꾼 비슷한 페이지는 구글이 도어웨이 페이지(doorway pages)로, AI로 대량 생산한 얇은 글은 대량 생성 콘텐츠 남용(scaled content abuse)으로 분류해서, 걸리면 도메인 전체 순위가 같이 떨어져. 네이버도 저품질 웹문서를 따로 걸러내.

그래서 기준을 이렇게 잡았어: 페이지마다 그 페이지에만 있는 실물이 있어야 한다. 우리 DB에 실제 제작 사례가 충분한 주제만 남기니까 24장이 나왔어. 그 이상 늘리면 같은 포트폴리오를 돌려쓰게 돼서 위험해져.

  • 실물 = 그 주제의 실제 VR 사례, 고객 이름, 콘텐츠 수, 그 업종에 맞는 활용법과 FAQ
  • AI가 맡는 일 = 레이아웃, 문구 다듬기, FAQ 초안, 구조화 데이터(JSON-LD)
  • 사람이 맡는 일 = 사례 고르기, 가격·기간 같은 사실 확인, 최종 검수

4. 어디에 어떻게 올리나 (레거시 기준)

🔴 SPA로 만들면 안 돼 클라이언트 렌더링 SPA는 크롤러에게 빈 HTML을 줘. 네이버 크롤러(Yeti)는 JS 렌더링이 약해서 본문이 아예 색인되지 않을 수 있어. 만드는 도구는 무엇이든 괜찮지만 빌드 결과물은 페이지마다 완성된 정적 HTML이어야 해 (정적 사이트 생성, SSG).
안 A: PHP 문서 루트에 정적 HTML 추가 (추천)안 B: 정적 빌드 → S3 + CloudFront
주소look360.kr/solutions/campus-vr-tourlook360.kr 앞에 CloudFront(E134ZI2PZY55NN)가 이미 있어서 같은 도메인 경로로 붙일 수 있음. 다만 경로별 오리진 설정을 추가해야 함
도메인 신뢰도기존 look360.kr의 신뢰도를 그대로 받음서브도메인이면 검색엔진이 별도 사이트처럼 취급할 수 있음
배포정적 HTML을 Look360_ksq1.2 저장소에 커밋 → paperclip 브랜치 push → 서버에서 git pull. 서버 설정 변경 없음 (🔧 처음엔 rsync라고 적었는데 틀렸어. 이 서버는 git 배포만 써)S3 업로드 + CloudFront 무효화. 인프라 추가
위험운영 서버 파일을 건드림 → 별도 디렉토리만 쓰고 기존 PHP는 손대지 않기운영 서버와 완전히 분리돼 안전

제안: 랜딩 원본은 별도 저장소에서 Astro 같은 정적 사이트 생성기로 만들고, 빌드 결과물만 안 A로 /solutions/ 아래에 올리자. 나중에 안 B로 옮겨도 빌드 결과물은 그대로 쓸 수 있어.

페이지마다 같이 넣을 것

  • 실제 VR 링크와 임베드 (레거시 VR 주소로 연결)
  • JSON-LD: Service, FAQPage, Organization
  • sitemap.xml에 추가하고 네이버 서치어드바이저와 구글 서치 콘솔에 제출
  • 제작의뢰 폼으로 가는 링크에 ?from=landing-campus 같은 출처 값 → 어느 페이지에서 문의가 왔는지 GA4와 문의 내역 양쪽에서 집계
  • 페이지끼리 서로 링크 (고민형 페이지가 업종 페이지로 연결하는 허브)

5. 네이버 블로그와 같이 굴리기

네이버 검색 결과에서는 블로그 탭이 웹사이트보다 위에 나와. 랜딩페이지는 주로 구글과 네이버 웹문서 영역을 잡는 거야. 랜딩 1장을 만들 때 같은 소재로 블로그 글 초안 1편을 같이 뽑아서, 블로그에서 랜딩으로 링크를 거는 구조로 가자. 블로그 활성화는 이미 진행 중이니까 랜딩 배치 일정에 블로그 주제를 맞추면 돼. 게시는 자동화하지 말고 사람이 직접 하는 걸 추천해 (네이버 블로그 자동 게시는 약관상 애매해).

6. 성과 측정

  • 배치마다 4주 뒤 확인: 색인된 페이지 수, 검색 노출·클릭 (서치어드바이저, 구글 서치 콘솔), 랜딩별 문의 수

  • B1~B3 결과가 괜찮을 때만 B4(지역)를 진행해.

7. 오빠가 확인해 줘야 할 것

  1. 실적 범위: 일부 확인 Campustown·경기관광공사는 우리 실적으로 확인됐어(2026-10-04). 남은 것: 기회의 경기(220)·오산시 징검다리교실(194)·서울관광재단(46)·남한산성(7). 확인 전이라 시안에서는 뺐어.
  2. 고객 이름 공개: 대학·기관 이름을 사례로 노출해도 되는지
  3. 레거시 VR 주소 형식: 해결 look360.kr/vr/{장소 도메인} (예: /vr/shinnam.es), 실응답 200 확인
  4. 제작의뢰 폼 경로: 해결 /?m=bbs&bid=pano_request&mod=write. 짧은 주소 /b/pano_request/write는 리라이트 규칙에 QSA가 없어서 ?from= 값이 사라지므로 쓰지 않아.
  5. 가격 공개 수준: "비용" 페이지에 가격대를 적을지, 결정 요소만 설명할지
  6. CloudFront 여부: 해결 이미 있어 (E134ZI2PZY55NN). 그래도 안 A가 더 단순해서 안 A로 가.
  7. 제작 기간: 「절차」 페이지에 넣을 단계별 평균 제작 기간 (DB에 근거가 없음)

8. look360.kr 배포와 구글 노출 실행 계획

⏸ 구현 정지 (2026-10-04 오너 지시) 아래 「확정이 필요한 것」이 정해질 때까지 look360.kr 쪽 작업은 시작하지 않아. 지금은 kabkee-decks의 시안만 있고, 시안에는 noindex를 넣어서 구글이 색인하지 않게 해 뒀어.

2026-10-04에 확인한 사실

  • look360.kr/solutions/…는 CloudFront를 거쳐 EC2 Apache로 가고, 지금은 404가 나와. 비어 있는 경로라서 기존 PHP 라우팅과 겹치지 않아.
  • robots.txt는 /solutions/를 막지 않아.
  • sitemap.xml은 사이트맵 인덱스이고 그 안에 sitemap-static.xml이 있어. 둘 다 sitemap.php가 만들어.
  • 운영 서버 배포는 git으로만 해 (rsync·scp 금지). CEO 배포 승인이 필요해.

진행 순서 (확정 후)

  1. 정적 HTML로 넣기: Look360_ksq1.2 저장소에 solutions/{slug}/index.html로 넣고, 공용 CSS·JS는 solutions/_assets/에 둬. 주소는 look360.kr/solutions/{slug}/야. 기존 PHP 파일은 건드리지 않아.
  2. 올리기 전 정리: 상단 시안 띠와 noindex를 빼고, canonical·og: 태그를 넣고, 제목 끝에 「| LOOK360」을 붙여. 상대 링크는 /solutions/… 절대 경로로 바꾸고, 사례 카드에는 실제 VR 썸네일 이미지를 넣어 (지금은 캔버스 그림뿐이라 이미지 검색에 걸릴 게 없어).
  3. 허브 페이지: /solutions/에 랜딩 목록 페이지를 하나 만들어.
  4. 사이트 안에서 링크 걸기: look360.kr 상단 메뉴(「VR제작의뢰」 옆)나 푸터에서 /solutions/로 링크를 걸어. 사이트맵만 있으면 구글이 중요하지 않은 페이지로 볼 수 있어.
  5. 사이트맵: sitemap.php의 sitemap-static.xml 목록에 랜딩 주소를 추가해.
  6. 배포: paperclip 브랜치에 push한 다음 서버에서 git pull을 해. CEO 배포 지시가 있어야 진행해.
  7. 색인 요청: 구글 서치 콘솔과 네이버 서치어드바이저에서 사이트맵을 다시 제출하고, 랜딩 주소마다 「색인 생성 요청」을 해.
