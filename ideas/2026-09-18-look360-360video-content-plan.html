A

이미 절반쯤 선언돼 있다 — 콘텐츠 모델

「어디에 담을 것인가」를 묻기 전에, 이 코드베이스가 이미 무엇을 약속해 뒀는지부터 읽는다.

A-1. 세 겹의 선언 vs 세 겹의 공백

video360 은 새로 만들 값이 아니다. 서버 enum, 어드민 등록 드롭다운, FE 7개 로케일 라벨 — 세 지면이 이미 이 값을 알고 있다. 반면 실데이터·런타임 분기·렌더 경로는 전부 비어 있다. 이 비대칭이 이번 기획의 실제 출발점이다.

지금 한 행을 넣으면 무슨 일이 생기나

pano_type='video360' 행 한 건이 어떤 360뷰에 붙는 순간, XML 빌더의 default 경로로 떨어진다. pano_width 가 없으면 XML 생성 자체가 throw 로 죽고(krpano-xml-builder.ts:1198-1200), 있으면 존재하지 않는 큐브 타일 6면을 요청해 전부 404 가 난다 — 에러 로그 한 줄 없이 조용히 깨진다. [실측: W1 census §9]

단일 이미지 폴백(:1157)조차 pano_type === 'sphere' 리터럴 일치를 요구하므로 video360 은 그 구명줄도 못 잡는다.

A-2. 「동영상이 섞이면 무엇이 깨지나」 — 13축 census

선행 조사 W1(IND-7535)이 l3_panorama·l3_vc_360view_pano·l3_vc_360view 를 읽는 모든 경로를 컬럼 단위로 열거해 실제로 파손되는 지점을 추렸다. 전문은 .artifacts/IND-7495-W1/census-pano-readers.md 에 있고, 여기에는 판정과 대표 좌표만 옮긴다.

한 가지는 이미 뷰어까지 흘러가고 있다

뷰어 응답 경로는 파노라마마다 pano_type 을 이미 내려보내고 있고 FE 가 === 'flat' 분기에 쓰고 있다 (views/VrViewer.vue:1533,1724,2628,2786). [실측] 즉 §F 의 구성요소 배지는 새 API 없이도 그릴 데이터가 이미 와 있다. 반면 어드민 목록 API 는 §12 대로 계약에 pano_type 이 없어 그쪽만 DTO 승격이 필요하다.

A-3. 모델 3안 비교

선례도 ①안 쪽이다. 이 코드베이스는 이미 「같은 테이블 + 문자열 종류 구분자」 로 동영상을 다루고 있다 — l3_vc_360view_media.media_type 은 image 1,137건 / youtube 1건, l3_360post_media.media_type 은 image 4,780 / youtube 310 / vimeo 1 로 프로덕션에서 돌고 있다. [실측] 다만 둘 다 display_order 시퀀스 안에 파노라마와 나란히 놓이는 「구성요소」가 아니다 — 전자는 panorama_uid FK 자체가 없고, 후자는 게시글 첨부다. 그러므로 ②안은 「이 테이블을 확장한다」가 아니라 신규 테이블을 만든다는 뜻이다.

추천 · A안 — 이미 선언된 값을 가동한다오너 결정 ①
  1. 스키마 변경 0줄로 시작한다. pano_type 은 ENUM 이 아니라 varchar(255) 라 ALTER 가 애초에 없다. [실측]
  2. 값은 video 가 아니라 video360 이다. 서버 enum·어드민 드롭다운·7개 로케일이 이미 이 철자로 굳어 있다 — 새 철자를 만들면 그 세 지면을 전부 어긋내게 된다.
  3. 정규화 위배는 인정하고 관리한다. 영상 행의 이미지 전용 컬럼은 NULL 로 남는다. pano_width 부재 시 throw 하는 지점(krpano-xml-builder.ts:1198-1200)에 타입 선분기를 먼저 세우는 것이 1순위 안전장치다.
  4. 3종 이상으로 늘어날 조짐이 보이면 그때 ②안으로 승격한다. ①→② 는 가법적이라 이행 가능하지만, ③ 으로의 이행은 되돌리기 어렵다.

B-2. 상태 머신 — 기존 어휘를 그대로 승계

새 어휘를 만들지 않는다. TileCreationStatus enum 이 이미 5개 값을 정의해 뒀고 (common/enums/panorama.enums.ts:14-20), 실제 분포도 확인했다 [실측]: completed 32,065 · "0" 281 · not_generated 35 · NULL 1. (선언된 pending/inprogress/error 는 현재 데이터에 0건이지만 어휘는 이미 존재한다.)

pending→ inprogress→ completed ｜ 실패 시 →error ｜ 변환 대상 아님 →not_generated
컬럼을 새로 팔 것인가, 있는 것을 쓸 것인가

tile_creation_status 를 영상에도 그대로 쓰면 컬럼 추가가 0개다. 다만 이 컬럼은 이름 그대로 「타일 생성」의 상태이고, 이미 과거에 두 번이나 오분류 정정 마이그레이션이 돌았던 컬럼이다 (migrations/20260720180000-FixSphereTileStatusMisclassified.ts 외 1건, 54건 정정). [실측] 여기에 의미를 하나 더 얹으면 다음 번 오분류 조사가 두 배로 어려워진다. 그래서 같은 어휘(값 5종)를 쓰되 컬럼은 video_encoding_status 로 분리하는 쪽을 추천한다 — 어휘 승계와 축 분리를 동시에 얻는다.

B-3. 해상도 사다리

360 등장방형 영상은 전체 구면을 한 프레임에 펼쳐 담고 사용자는 그중 FOV 90~100° 만 본다. 체감 선명도를 평면 영상 기준으로 맞추려면 원본이 그 몇 배여야 한다 — 통상 4K equirect 가 체감 HD 급, 8K equirect 가 체감 4K 급이라는 것이 업계 경험칙이다. [추정] 그런데 반대편에 제약이 있다: 모바일 하드웨어 디코더의 실질 상한이 4K 다 — iOS 는 A9 이상에서 HEVC 최대 2160p, VP9 은 A14(iPhone 12) 이상에서 최대 4K 이며, iPhone 라인업의 8K 하드웨어 디코딩 근거는 찾지 못했다. [문서근거]

이 둘을 맞물리면 사다리는 자연스럽게 「원본은 크게 보관하되, 재생 사다리의 천장은 4K」 로 정해진다.

코덱은 H.264/MP4 를 1순위로 고정한다. krpano videoplayer 공식 문서가 명시한 지원 포맷이 H264(mp4/m4v/mov) · WebM · Ogg Theora 3종뿐이고, HEVC/VP9/AV1 은 문서에 언급이 없기 때문이다 [문서근거] (실제로는 브라우저 네이티브 <video> 코덱 지원을 물려받을 여지가 있으나 [추정] 이라 계약으로 삼지 않는다). 4K H.264 는 HEVC 대비 파일이 커진다는 대가를 치르지만, 「재생이 안 되는 작은 파일」보다 「재생되는 큰 파일」이 낫다. WebM/VP9 을 2순위 트랙으로 병기하는 것은 선택 사항이며, 이 레포의 videourl="a.mp4|b.webm" 파이프 구분 다중 포맷 인프라가 이미 그 형태를 지원한다 [실측].

근거 — ① dev 머신에 /usr/bin/ffmpeg 6.1.1 과 /usr/bin/ffprobe 가 이미 설치돼 있다 [실측]. ② 코드 레포 어디에도 ffmpeg 참조가 0건 이라 기존 변환 파이프라인과 충돌할 코드가 아예 없다 [실측]. ③ MVP 단계의 건수(수십 건)에서는 관리형 서비스의 고정 학습비·연동비가 변환비보다 크다.

단서 — 운영 서버의 ffmpeg 설치 여부는 이 조사에서 확인하지 못했다 [추정]. 구현 착수 전 운영 서버에서 ffmpeg -version 을 직접 재는 것이 첫 작업이어야 한다. 부재로 확인되면 설치(패키지 1개) 또는 관리형 전환 중 택일이며, 그때는 이 결정을 다시 올린다.

되돌아갈 길 — 변환 호출을 얇은 어댑터 뒤에 두면 서버 ffmpeg → 관리형 전환은 구현 교체 1개소로 끝난다. 지금 관리형을 고르는 것보다 나중에 관리형으로 가는 것이 싸다.

B-5. 백업 전략과의 충돌 — 반드시 먼저 정할 것

2026-09-14 확정된 파일 백업 전략은 AWS Backup 대신 로컬 백업 + 버저닝 30일, 매일 04:00 dsgn 에서 바뀐 장소만 다시 받는 증분 갱신, 보관은 30일 전부 + 월간 12개월 + 기준본, 예상 월 1,500~4,500원이다 [문서근거: reports/2026-09-14-look360-file-backup-strategy.html]. 이 설계는 「파일이 아주 많지만 개당은 작다」(현재 버전 1,656만 개)를 전제로 균형이 잡혀 있다. 영상이 들어오면 그 전제가 정확히 뒤집힌다 — 개수는 적고 개당이 수 GB.

추천 · 원본만 백업 · 사다리는 제외오너 결정 ⑥
  1. 원본(마스터)은 백업 대상에 넣는다. 유일본이고 재생성이 불가능하다. 대신 버저닝에서는 제외하거나 보관 기간을 짧게 둔다 — 영상 원본은 이미지처럼 덮어쓰기가 잦은 자산이 아니다.
  2. 사다리(L1~L3)와 포스터는 백업에서 제외한다. 원본이 살아 있으면 ffmpeg 한 번으로 전부 되돌아온다. 이 한 줄이 100건 기준 200GB 를 백업 대상에서 걷어낸다.
  3. 제외는 경로 접두(prefix) 규칙으로 건다. 확장자나 파일 크기로 고르면 다음 사람이 규칙을 못 읽는다 — 사다리 산출물을 별도 접두 아래로 몰아넣는 것이 설계 조건이다.
  4. 「사다리는 백업 안 함」을 문서에 적는다. 적어 두지 않으면 사고 복구 시점에 「왜 여기만 비어 있지」 로 시간을 잃는다.
C

krpano 가 할 수 있는 것 · YouTube 가 막는 것

자체 호스팅 영상과 YouTube 임베드는 같은 「360동영상」이 아니다. 기술적으로 다른 물건이다.

C-1. krpano videoplayer 능력

이 레포가 싣고 있는 플러그인은 krpano 1.23.3 (build 2025-11-15) 이다 — 파일 헤더 주석에서 직접 확인했다 [실측]. 본문은 krpano 표준 난독화라 소스 조사가 불가능해, 이하는 공식 문서와 이 레포의 실사용 호출 패턴을 교차검증한 결과다.

이 레포가 이미 밟은 지뢰 4개 — 설계 단계에서 피할 것

① onvideocomplete 이벤트 유실 — 브라우저/코덱에 따라 안 온다. KrpanoStoryAdapter.js 가 time/totaltime/iscomplete 폴링 폴백 타이머를 병행한다(파일 833-898줄). [실측]

② 자동재생 차단 시 videoplayer 가 깨진 상태로 남음 — 그래서 stop() → play() 순서로 내부 상태를 리셋한다. [실측]

③ IND-3933 — type="video" 핫스팟 클릭이 src 를 못 잡음. 최종 해법은 krpano 를 재생에서 빼고, 트리거만 발행해 Vue 쪽 VrVideoPopup.vue 가 HTML5 <video> 로 재생하는 완전 우회였다. [실측] 즉 이 레포에서 「비디오 핫스팟 재생」은 krpano 경로가 아니다.

④ style 속성 안에서 %videourl% 변수치환이 동작하지 않음 — 빌더가 값을 직접 문자열 주입으로 우회 중(krpano-xml-builder.ts:208-220). [실측]

C-2. YouTube 360 임베드 — 전제 확정

「교차 출처 iframe 이라 krpano 텍스처로 못 쓴다」는 전제는 맞다. W2 가 Playwright 로 직접 계측해 확정했다 [실측]. YouTube 는 iframe 내부에서 자체 WebGL 구체 매핑을 수행하고, iframe 은 youtube.com 오리진이라 postMessage 리모컨 API 로만 통신된다. krpano 의 <sphere url="plugin:video"> 는 자신이 제어하는 <video> 의 텍스처 업로드가 필요한데, 교차 출처 프레임은 캔버스를 오염(tainted)시켜 texImage2D/getImageData 가 보안 예외를 던진다 — 브라우저 표준 동작이다 [문서근거: MDN·WHATWG].

그러므로 YouTube 360 은 「뷰어 영역 위에 iframe 을 얹고 YouTube 자체 360 조작을 쓰는」 방식 하나뿐이고, 그 대가로 krpano 기능을 잃는다.

C-3. 브라우저 매트릭스

「이게 360 영상인가」를 어떻게 아는가

oEmbed 응답에는 360 여부 필드가 없다 [문서근거]. YouTube Data API v3 의 fileDetails.videoStreams[].projectionType 은 영상 소유자만 조회 가능해 제3자 URL 붙여넣기에는 못 쓴다 [문서근거].

W2 가 찾아낸 실용적 판별법: IFrame API 로 로드 후 getSphericalProperties() 를 호출해 빈 객체면 일반, 값이 채워지면 360 [실측]. 다만 공식 문서가 「이걸로 판별하라」고 쓴 적은 없다 — 문서화되지 않은 실동작이라 YouTube 사양 변경에 취약하다. 등록 UI 에서는 이 판별을 차단이 아니라 경고로 쓰는 것이 안전하다.

C-4. 적응형 전송 — HLS/DASH vs 해상도별 MP4

추천 · 해상도별 MP4 + 수동 화질 선택 UI구현 기본값

결정적 근거 — 적응형 스트리밍의 장점은 실재하지만, krpano 파노 텍스처에 HLS/DASH 를 쓰는 경로 자체가 공식 문서에 없다. 미검증 경로 위에 인프라를 새로 세우는 비용이 너무 크다.

자동 판정은 보조로만 — Network Information API 는 Chrome 계열 전용이고 Safari(iOS 포함)·Firefox 는 전 버전 미지원이다 [문서근거]. iOS 사용자에게는 자동 판정이 아예 불가능하다. 게다가 무리하게 높은 단을 고르면 4K 상한의 하드웨어 디코더에서 끊긴다. 따라서 수동 화질 선택 UI 는 선택이 아니라 필수 안전장치이고, 자동 판정은 「기본값 제안」까지만 한다.

D

뷰어 UX — 파노라마 줄에 영상이 한 칸 끼어들 때

좌표: views/VrViewer.vue · components/vr-viewer/VrPanoList.vue · VrPanoListItem.vue (전부 읽기만 했다)

D-1. 하단 목록 — 썸네일 + 제목

오너 요구는 「하단 목록에 썸네일과 제목이 보일 것」이다. 이건 이미 그렇게 돼 있다. VrPanoListItem.vue 는 120×80 썸네일 위에 .vr-pano-item__name-overlay 로 제목을 하단 그라데이션 위에 얹고 있다 [실측]. 영상 항목이 추가로 필요로 하는 것은 딱 세 가지다.

  • ① 포스터 썸네일 — 영상에는 tile_info.thumb_url 이 없으므로 인코딩 단계에서 뽑은 poster 를 같은 슬롯에 채워 넣는다. 안 채우면 pano-thumb.util.ts SSOT 가 깨진 이미지를 반환한다(§A-2 축10).
  • ② 구성요소 배지 — 「이건 영상이다」를 썸네일만 보고 알 수 있어야 한다 → §F.
  • ③ 재생 시간 — 우하단에 3:42 형태. 코너 충돌 검토는 §E-2.
코너 슬롯 현황 — 배지를 어디에 둘 수 있나

현재 썸네일 코너는 좌상단=열람 체크(.vr-pano-item__check), 우상단=포스트 수 배지(.vr-pano-item__badge-count), 하단 전폭=이름 오버레이가 이미 점유하고 있다 [실측]. 남은 자리는 좌하단 하나뿐이고, W3 가 배지를 거기에 배치한 것이 바로 이 때문이다. 재생 시간을 우하단에 두려면 이름 오버레이와의 겹침을 먼저 풀어야 한다.

D-2. 재생 컨트롤 · 자동재생 정책

자동 QC 가 못 잡은 4건이다

IND-4859 의 네 가지는 자동 QC 가 전부 PASS 로 통과시킨 뒤 보드 직접 체감검증에서만 드러났다 [실측]. 정적 검증으로는 「iframe 이 300×150 으로 렌더된다」·「두 플레이어가 동시에 소리를 낸다」를 잡을 수 없다. 이번 구현의 DoD 에는 체감검증 항목을 명시적으로 넣어야 한다.

D-3. 전환 · 종료 시 동작

파노라마 ↔ 영상 전환에서 지켜야 할 규칙은 「떠날 때 반드시 멈춘다」 하나로 요약된다. 다른 씬으로 이동했는데 오디오가 남아 흐르는 것이 가장 흔한 실패다.

  1. 영상 → 파노라마: 재생 중지 + currentTime 리셋(또는 위치 기억 — ④와 함께 결정) + iframe 이면 pauseVideo() 호출 후 DOM 제거.
  2. 파노라마 → 영상: krpano 씬은 그대로 두고 영상 레이어를 위에 얹는다. krpano 를 언로드하면 돌아올 때 재초기화 비용이 든다.
  3. 자이로/드래그 입력 경합: 영상 레이어가 떠 있는 동안 krpano 포인터 이벤트를 막는다 — 안 그러면 드래그가 뒤의 파노라마를 돌린다.
  4. 재생 위치 연속성: IND-4859 FAIL ④ 가 정확히 이것이었다 — 라이트박스를 닫았다 열면 처음부터 다시 재생됐고, 오너가 나중에 명시 지시로 연속재생을 추가시켰다 [실측]. 이번엔 처음부터 넣는다.

영상이 끝나면 — 옵션 비교

추천 · ㉡ 다음 구성요소로 진행 (되돌릴 수 있게)

VrVideoPopup.vue 의 handleVideoEnded 가 이미 「끝나면 지정 씬으로 이동하고 시선까지 맞춘다」를 구현해 두었다 — 새 패턴을 만들 필요가 없다. 다만 자동 진행 직전 2~3초의 취소 가능한 안내를 붙여 ㉠ 으로 빠져나갈 길을 남긴다. IND-4833 오너 스펙의 ④ 「일시정지 상태에서는 자동 넘김이 멈춰야 한다」도 그대로 지킨다 [실측].

D-4. 영상 항목은 다른 기능들과 어떻게 맞물리나

§A-2 census 의 각 축에 1:1 로 대응시킨 처리 방침이다.

E

목록 UX — 뷰어 안 「VR목록」

좌표: components/vr-viewer/tabs/VrListTab.vue (읽기만)

「vr list」를 무엇으로 읽었나

오너 문장의 「vr list」를 1차로 뷰어 안 「VR목록」 탭·하프시트로 해석했다. VrListTab.vue:130 이 VrPanoListItem 을 그대로 재사용하므로 썸네일 규격이 PC 바와 동일한 120×80 이다 [실측] — 즉 §F 배지가 한 번에 두 지면을 덮는다.

/vr-list 카드(목록 페이지)에도 「360동영상 포함」 표기를 할지는 임의로 정하지 않았다 — §H 오너 결정 ④ 로 올린다.

E-1. 썸네일을 누르면 재생된다

현재 VrListTab 의 항목 클릭은 handleItemClick(item) → 해당 씬으로 이동이다 [실측]. 영상 항목도 같은 한 번의 클릭으로 끝나야 한다.

  1. 클릭 = 재생 시작. 「선택 → 다시 재생 버튼」의 2단계를 만들지 않는다.
  2. 목록은 열린 채로 둘지 닫을지 — 모바일 하프시트는 닫고, PC 는 열어 둔 채 재생하는 것을 추천. PC 에서 목록이 닫히면 다음 항목으로의 이동이 멀어진다.
  3. 재생 중 항목은 목록에서 상태로 구분 — 기존 「현재/방문」 체크 인디케이터를 그대로 쓰고 새 상태를 발명하지 않는다.

E-2. 재생 시간 표기

이 값을 담을 곳이 현재 없다. l3_panorama 어디에도 길이 컬럼이 없다 [실측] — video_duration_sec(또는 tile_info.video.duration)이 필요하고, 값은 인코딩 단계의 ffprobe 가 공짜로 준다. YouTube 는 oEmbed 응답에 길이가 없어 IFrame API getDuration() 또는 Data API 가 필요하다 [추정] — 등록 시점에 한 번 받아 저장해 두는 편이 낫다.

E-3. 호버 미리보기 (선택)

PC 에서 썸네일 호버 시 짧은 무음 미리보기를 재생하는 것은 체감이 좋지만, 1단계에서는 넣지 않기를 추천한다. 사다리 최저단(L3)이라도 호버할 때마다 수 MB 를 받는다 — 목록을 훑는 동작 하나가 전송비를 곱한다. 넣는다면 전용 미리보기 클립(3초·저해상도·별도 산출물)을 인코딩 단계에서 함께 만들어야 하고, 그건 사다리에 한 단이 더 붙는다는 뜻이다. 2단계 과제로 남긴다.

F

구성요소 종류 배지

아래 목업은 이미지가 아니라 이 문서 안에서 실제로 렌더되는 HTML/SVG 다 — W3(IND-7537) badge-mockup.html 을 그대로 인라인했다.

두 층위를 먼저 구분한다 [문서근거: utils/contentTypeChip.js]
① 콘텐츠 칩(기존) — 카드 이미지 아래, 알약(pill), 타입별 유채색. 「이 콘텐츠가 VR 인가 360포스트인가」
② 구성요소 배지(신규) — 썸네일 이미지 위 코너, 원형, 무채색 다크 반투명. 「이 한 칸이 파노라마인가 영상인가」
→ 형태 · 위치 · 색 · 문맥 4축을 모두 다르게 가져가 한 화면에 같이 나와도 혼동되지 않게 설계했다. 위치는 기존 코너 오버레이(좌상단 체크 · 우상단 포스트수)와 겹치지 않는 좌하단으로 고정.

안 A — 아이콘 전용 (원형 배지, 좌하단)

라벨 없이 아이콘 형태만으로 4종 구분: 구면 링 / 사각+수평선(flat) / 원+재생(업로드) / 둥근사각+재생(YouTube). 다국어 영향 없음.

안 B — 아이콘 + 라벨 (필 배지, 좌하단)

텍스트 병기로 즉시 이해도는 높지만, 라벨 폭이 다국어와 최소 썸네일 크기에 직격된다.

로드맵과 오너 결정 목록

🚫 이 절의 이슈 분해는 문서 안의 목록일 뿐이며 실제 발주가 아니다. 구현 발주 여부는 오너가 따로 결정한다.

H-1. MVP → 확장

왜 YouTube 를 먼저 하는가

YouTube 형은 인프라가 0 이다 — 저장·변환·전송·백업 전부 남의 비용이고, 등록 폼도 §G-3 대로 이미 있는 것을 옮기면 된다. 그런데 「구성요소 줄에 파노라마 아닌 것이 한 칸 낀다」는 핵심 난제는 똑같이 전부 겪는다 — 집계 오염, 대표 이미지 선정, 핫스팟 도착지, XML 빌더 분기. 가장 싼 비용으로 가장 어려운 문제를 먼저 푼다. 파일 업로드는 그 위에 얹으면 된다.

H-2. 이슈 분해 후보 · 선후관계

1번이 먼저다. 안전장치 없이 데이터가 먼저 들어가면 그 순간 해당 360뷰의 XML 생성이 죽거나 조용히 깨진다. 등록 UI 보다 렌더 방어가 앞선다.

H-3. 오너 결정 목록

① 콘텐츠 모델 3안 중 무엇인가

선택지 — ㉠ pano_type='video360' 확장(A안) ／ ㉡ 별도 동영상 테이블 + 구성요소 종류 컬럼 ／ ㉢ 다형 연결(component_type+component_uid)

추천 ㉠ — DDL 0줄, 기존 JOIN 무파손, 백필 0건, 롤백은 값 되돌리기. 무엇보다 이 값은 이미 enum·어드민·7개 로케일에 선언돼 있다. ㉢ 은 21개 파일의 JOIN 전량 재작성이라 질적으로 다른 규모다. 대가는 정규화 위배 — l3_panorama 한 테이블이 두 성격을 담는다. 구성요소 종류가 3종 이상으로 늘면 그때 ㉡ 으로 승격한다.

② YouTube 임베드로 krpano 기능을 잃는 것을 감수하는가

잃는 것 — 핫스팟 · 360포스트 마커 · krpano VR 모드 · 구체 화면 캡처. 지키는 것 — 360 조작 자체 · 자이로 · 지도 연동 · 음소거 자동재생 · 재생 제어. (§C-2)

추천: 조건부 수용 — 기술적 대안이 없다. 교차 출처 캔버스 오염은 브라우저 보안모델이라 우회가 원천 차단이고, 다운로드·재인코딩·프록시는 YouTube 약관 위반 소지가 명백하다 [문서근거]. 대신 「영상 구성요소는 핫스팟·포스트를 갖지 않는다」를 제품 규칙으로 명문화해 사용자가 기대를 갖지 않게 한다. 핫스팟이 꼭 필요한 영상은 파일 업로드형(2단계)으로 유도한다 — 그쪽은 krpano 텍스처 재생이 가능하다.

③ 트랜스코딩 — 서버 ffmpeg vs 관리형 서비스

추천: 서버 ffmpeg 로 시작 — dev 에 6.1.1 이 이미 있고, 레포에 ffmpeg 참조가 0건이라 충돌할 기존 파이프라인이 없다. MVP 건수에서는 관리형의 연동비가 변환비보다 크다. 단, 운영 서버 설치 여부는 미확인 [추정] — 2단계 착수 전 실측이 선행 조건이다(분해 #11). 변환 호출을 어댑터 뒤에 두면 나중에 관리형으로 갈아타는 비용이 1개소로 끝난다.

④ /vr-list 카드에도 「360동영상 포함」 표기를 하는가

선택지 — ㉠ 표기 안 함 ／ ㉡ 콘텐츠 칩 옆에 보조 표기 ／ ㉢ 카드 썸네일 위에 구성요소 배지까지 노출

추천 ㉠ → 2단계에 ㉡ — /vr-list 카드는 「콘텐츠 종류」 층위(VR/360포스트/외부VR)를 말하는 자리다. 여기에 「안에 영상이 들어 있다」는 구성요소 층위를 섞으면 §F 에서 4축을 들여 분리한 두 층위가 첫 화면에서 다시 붙는다. 먼저 뷰어 안에서 배지가 자리를 잡은 뒤, 실제로 「영상 있는 VR 만 찾고 싶다」는 요구가 관측되면 그때 필터와 함께 넣는 것이 순서다. — 이 항목은 W4 가 임의로 확정하지 않고 오너에게 올린다.

⑤ shot_type(항공·고고도)을 구성요소 배지에 넣는가

실측 분포 — general 31,956 · aerial 135 · highaltitude 10 · 이상치 8. 항공/고고도 합쳐 전체의 0.4% 미만 [실측].

추천: 넣지 않는다(W3 rationale 인용) — ① 좌하단 배지 슬롯이 이미 4종으로 차서 5번째 축을 얹으면 48×36 에서 배지 2개가 겹친다. ② 0.4% 를 위해 전 화면에 설계 복잡도를 더한다. ③ 촬영 방식은 배지보다 「VR목록」·상세의 텍스트 메타가 맞는 자리다 — 실제로 SHOT_TYPE_KEYS 라벨이 이미 그렇게 쓰이고 있다 [실측]. 대안 — 원한다면 우상단 보조 배지가 가능하나, 포스트 수 배지와 자리가 충돌해 예외 처리가 필요하다.

⑥ 영상 원본·사다리를 백업 대상에 넣는가

추천: 원본만 · 사다리 제외 — 사다리는 원본에서 재생성 가능한 파생물이라 백업할 이유가 없다. 100건 기준 200GB 를 백업 대상에서 걷어낸다. 제외는 경로 접두 규칙으로 걸고(확장자·크기 기준 금지), 「사다리는 백업하지 않는다」를 백업 전략 문서에 명시한다. 원본은 유일본이라 반드시 포함하되 버저닝 30일에서는 제외하는 것을 함께 검토한다 — 영상은 덮어쓰기가 잦은 자산이 아니다. (§B-5)

⑦ 판매자 스튜디오에도 등록 UI 를 여는가

사실 확인 — 스튜디오에는 현재 파노라마 등록 UI 자체가 없다 [실측]. 따라서 이건 분기가 아니라 신설이다.
